# 43. An anime's identity is `Media.Id`; status is a PER-ACCOUNT question (download = OR, deletion = AND)

**Location:** `anilist/anilist.go` (`DedupeByMedia`, `GetAnimeInfo`, `GetListStatusesByMediaIDs`, `GetMediaIDForEntry`, `AniListUserExists`), `files/filemanager.go` (`AnimeIDsMarked`, `MarkAnimeIDs`), `daemon/verification.go` (`searchAnilist`, `fetchListStatuses`, `deletableMediaIDs`, `allAccountsAgreeOnDelete`), `daemon/migration.go` (`MigrateAnimeIDsToMedia`), `api/endpoint_animes.go`.

**What it looks like:** three things that look overdone — `GetAnimeInfo` takes the username list and makes one request per account to fetch ONE anime; `DedupeByMedia` warns in the comment that nobody may read the result's `Status`; and the deletion vote needs every account's status of the anime, not just whether it shows up in a delete-status list. A fourth, under Migration: the completion mark is kept twice (config field and a marker file in the data dir), either half skips, and the missing half is backfilled.

**Why it's right:** `MediaList.Id` is the **entry** id, which is per account — the same anime on two accounts arrives as two entries with different ids and the same `Media.Id`. While the stored `AnimeID` was the entry id, it pointed at **one** of the accounts, and `GET /animes` listed the anime twice: once under the `id:<AnimeID>` key from disk and once by name, because the other account's entry matched nothing known (real bug: "From Old Country Bumpkin to Master Swordsman II", entries 488911345 and 583631757, media 194829). Worse than the duplicate: which entry "won" depended on progress, so the id stored on disk **changed** as the user watched, and status deletion, per-anime settings and the detail screen started looking for an id that half the records did not have.

With `Media.Id` as identity that disappears by construction. What remains is what a unique identity does *not* solve: each account has its own `status` and `progress` for the same media, and collapsing the two into one entry means choosing. The choices are deliberately asymmetric, because the errors do not cost the same:

- **`progress`: the LOWEST among the accounts** (`DedupeByMedia`). An episode is only "watched" when every account has seen it; erring high deletes an episode someone has not watched yet.
- **Download: OR** — ONE account having the anime in a download status is enough. That already falls out of the union of lists in `searchAnilist`, since each fetch is filtered by `status_in` on the server.
- **Deletion: AND** — EVERY account that has the anime must have it in some deletion status, and they need not be the same (`DROPPED` on one and `COMPLETED` on another deletes). An account that **does not track** the anime does not vote; one that has it in a neutral status (`PLANNING`) **vetoes**. Distinguishing those two cases is why the pass asks each account for its status of every anime **with an episode on disk** (`fetchListStatuses`, one `mediaId_in` per 50): a delete-status list only brings the deletable ones, so "it did not come back in the list" is ambiguous. **Amendment (see [#130](130-status-deletion-asks-anilist-only-about-the-animes.md)):** this used to be the whole delete-status lists plus a `GetMediaListStatus` tie-break per account that didn't list a candidate; that blew the rate limit every pass, and the per-on-disk query answers both at once.

Direct consequence: **nobody may read the `Status` of the dedup winner** — it belongs to an arbitrary account. Who answers about status is `deletableMediaIDs`.

**Migration:** `MigrateAnimeIDsToMedia` resolves each old `anime_id` via `GetMediaIDForEntry` and rewrites `downloaded_episodes` and `anime_settings`, marking `anime_ids_are_media_ids` on the config and in the data dir. It runs at boot **and** at the top of the verification pass, and the pass **aborts** until it has run: with ids in the old format nothing on disk matches AniList, and a pass in that state would re-download the entire library. It only writes after resolving everything, so a network failure in the middle does not leave half converted. Entries that no longer exist on AniList (404) keep the old id and are only logged — the episodes stay on disk. **Amendment (2026-11-23):** an entry that resolves but belongs to an account **not** in `anilist_usernames` also keeps its id (`GetMediaIDForEntry` returns the owner). The completion mark lived only in `config.json` then (see the second amendment), so a data dir moved to another machine with an older config reruns the migration on ids that are already media ids — and entry and media ids share one integer space, so a media id "resolves" to a stranger's entry. Real case: media 208025 ("I'm Dating a Dark Summoner") is also another user's entry pointing at media 11583, and the rerun moved the episode there, splitting the anime in two. A genuine legacy entry id is always the user's own, so ownership separates the cases at no extra request. Known limit: "own" means in `anilist_usernames` **when the migration runs** — a legacy entry of an account since removed from the config also keeps its entry id (logged under `ids_kept_not_own_entries`) and, like a 404, never matches AniList again. Accepted: it needs a pre-v2.1.1 install that dropped an account before upgrading. A configured name that matches **no** AniList account (renamed since) would turn every legacy entry foreign and close the migration with nothing converted — the next pass would then re-download the library. So when there is anything to migrate, each name in `anilist_usernames` is checked first (`AniListUserExists`, one request per account); a missing one aborts with nothing written and the mark off, and the pass stays blocked until the config is fixed. Not "abort when every entry is foreign": that is exactly what the legitimate rerun on media ids looks like. **Second amendment (2026-11-23):** the completion mark now also lives in the data dir — an `anime_ids_are_media_ids` marker file next to `downloaded_episodes` — so it moves with the data instead of depending on the `config.json` that came along. Either half skips the migration, and a run that finds only one writes the other (an install migrated before the marker gets it backfilled from the config; a marked data dir with an older config gets the config field back). The owner check stays as defence for a data dir moved **before** it was ever marked. Completing the mark on an already-migrated install is best effort: a failed write or an unreadable marker is logged and the pass goes on (the ids are media ids either way; a read-only data dir must not block every pass). Only a run that converted ids fails, and only when **neither** half could be written. Known limit: the backfill trusts the config half, so a pre-v2.1.1 data dir copied under a config that already has the flag on gets marked as migrated for good — the old code skipped it too; what is new is that the wrong mark now outlives the config. Accepted: it takes hand-copying old data into a newer install.

**Don't "fix" by:** deduplicating by name (two distinct animes can share an English title, and the name of a record that only came from `episodes.json` does not come from AniList); taking `media { id }` out of `GetFrontendAnimeList`/`GetAllCurrentAnime` for "complexity" (it is a scalar, and without it the dedup key is `0` — every entry falls into the "no media id" branch and the bug comes back whole, silently); branching on `MediaList.Status` after the dedup (it belongs to a lottery account); swapping the veto for "any account in a deletion status deletes" (one account completing an anime is enough for the episodes to vanish from under whoever is still watching); treating an account whose fetch failed as agreement (would turn a passing AniList failure into a file deletion, which is irreversible); running the migration without the completion mark (the second time it would read media ids as entry ids); dropping `user { name }` from `GetMediaIDForEntry` or the owner check in `MigrateAnimeIDsToMedia` as "redundant with the mark" (the config half of the mark is only as good as the `config.json` that came along, and a data dir moved before it got the marker has only that half); dropping the account-exists check before the owner check (a renamed account would mark the migration done with nothing converted); dropping either half of the mark or requiring both to skip (requiring both would rerun every install migrated before the marker existed, on ids that are already media ids).
